// threat_context

The problem, in two clicks

01WHY THIS EXISTS

Most people don't get hacked by movie-style exploits. They get hacked by an ordinary link and an ordinary password. Both look fine until they aren't.

  • Email is the #1 lure. Phishing arrives disguised as urgent account alerts, invoices, KYC and password resets.
  • Lookalike links lie. @ tricks, punycode and bonus subdomains hide the real destination in plain sight.
  • Weak passwords fall fast. Short or reused passwords are guessable offline, long before any alarm rings.

Context: phishing remains a top initial-access vector — Verizon DBIR · guidance: NIST SP 800-63B · sources below ↓

      // how_it_works

      Transparent, boring, honest math

      STEP 1

      Input stays on-device

      The page parses your URL string or measures your password in JavaScript, in this tab. There is no server-side component — nothing to intercept, nothing to leak.

      fetch("/analyze") → never happens

      STEP 2

      Signals get scored

      Links: scheme, IP hosts, label depth, length, @ placement, punycode, risky TLDs, brand-lookalikes and more are weighted into a 0–100 risk score → SAFE / SUSPICIOUS / RISKY.
      Passwords: length (NIST-weighted), entropy estimate, common-list match, sequences and repeats → five strength bands.

      heuristic_score = Σ signals − patterns

      STEP 3

      You get the reasoning

      Every point on the score is explained in plain language — which signal fired, why it matters, and what to do next. No black boxes, no “trust the badge”.

      score → explanation → action

      // known_limits

      What this can't see

      01

      False positives happen

      Long, parameter-heavy links from Google, GitHub or password managers can score “suspicious”. Context matters — when in doubt, navigate manually.

      02

      False negatives happen

      A freshly-registered phishing domain with clean strings can sail through lexical checks. This is a first line of defense, not the last.

      03

      No live threat data

      We do not query WHOIS, DNS, reputation feeds or blocklists, and we do not follow redirect chains. A real redirect count requires resolving hops — we don't hide the fact that we don't.

      04

      HTTPS ≠ safe

      Attackers happily buy certificates. HTTPS only proves encryption in transit — this tool tells you when a link uses HTTP, and never treats HTTPS as proof of legitimacy.

      05

      Common-password list is finite

      Our local list covers the most frequently cracked passwords (~150 entries). A password not on it isn't automatically strong — and our check is not a “have I been pwned” service.

      06

      Meters are estimates

      Strength meters guide, they don't guarantee. Research on password meters shows they shape behavior — treat this one as a well-informed hint, then use MFA everywhere you can.

      Dependency transparency: layout uses Bootstrap 6 (CDN) and webfonts. All analysis — both tools — works locally with zero network calls. “Fully offline” applies to the logic, not to the CDN chrome.
